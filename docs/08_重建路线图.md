# 08 · 重建路线图

> 本章回答：**如果从零做一套功能一样的系统，怎么拆、做多久、先做什么、哪些可以不做。**
> **v2（2026-10-24 修订）**：工作量口径从"后端+前端分离统计"改为**按 `12_功能需求规格FRD.md` 的模块逐个统计（每个模块含前后端）**，
> 消除重复计算；新增 **MoSCoW 优先级裁剪**、**MVP 范围**、**团队配置与排期样例**、**逐模块交付物清单**。
> 总量与 v1 基本吻合（1,320~1,920 vs 1,540~2,300），但**可直接用于排期**。

## 一、先做三个决策（决定后面一切）

### 决策 1：移植还是重写？

| 路线 | 做法 | 工作量 | 评价 |
|---|---|---|---|
| A. Lift & Shift | 原样搬到新硬件 | 15~25 人天 | 治标不治本，Asterisk 1.4/Node6/Java6 全部 EOL 照旧 |
| B. Replatform | 换底座（新 OS/容器/Mongo 新版），代码小改 | 40~60 人天 | 性价比高，但技术债继续背着 |
| C. **重写（推荐）** | 用现代栈重建，功能对齐 | **1,320~1,920 人天** | 贵，但能真正解决问题 |
| D. 绞杀者渐进 | 外围新写、核心后换，双轨并行 | 首年 60~100 人天 | 风险最低，适合"不能停机"的场景 |

**建议**：目标是"能长期演进的系统" → **C 或 D**；只是"先救活" → **B + 立即治理**（见第六节）。

### 决策 2：语音引擎选型（最关键，且最不可逆）

| 选项 | 优点 | 风险 |
|---|---|---|
| **Asterisk 20 LTS** | 与现网语义最接近（仍保留 chan_sip）、AEL 可沿用、迁移成本最低 | 仍需处理 chan_sip→PJSIP 的长期演进 |
| Asterisk 22 LTS | 最新 LTS | **chan_sip 已删**（21 起），`res_monitor` 也删了 → **录音 `Monitor()` 全废，须改 `MixMonitor`** |
| FreeSWITCH | 并发与稳定性更好，ESL 更现代 | 现有 29 类节点的 AEL 语义要全部重写成 dialplan/Lua |
| 云厂商 CPaaS | 最快，免运维媒体层 | 失去 IVR 编排深度、长期成本与被锁定 |

**推荐**：**Asterisk 20 LTS 两步走** —— 20 仍保留 chan_sip（配置几乎可平移），
稳定后再 dual-stack（PJSIP 6160）批量迁分机，最后才考虑 22。

### 决策 3：协议与前端

- **协议**：新系统内部一律 REST/JSON；**面向老前端必须保留一层 `action` 协议适配器**（否则 102 万行前端全改）。
- **前端**：不要复刻 ExtJS。坐席工作台用 Vue3/React 重写（约 500~800 人天），
  但**菜单与权限模型照抄**现网（`cc_app_menu` + `app_role` 的 `limits/scope` 三段式设计是合理的，直接复用）。

## 三、优先级裁剪（MoSCoW）—— 不是所有功能都要做

现网有大量**低频/被注释/能力残缺**的功能。重建时建议先砍：

| 优先级 | 模块 | 理由 |
|---|---|---|
| **Must**（不做就不叫呼叫中心） | P0 底座、P1 媒体、P2 话务核心、P3 IVR（**放音/按键/转技能组/时间/转坐席 5 类节点**）、P4 通话记录、P16 计费 | 承载核心话务 |
| **Should** | P5 CRM、P6 工单、P12 监控质检、P17 报表、P18 运维 | 日常运营必需 |
| **Could** | P7 短信、P8 问卷、P9 知识库、P10 IM、P11 邮件、P13 组织权限、P14 批量外呼、P15 对接 | 按客户实际需求选 |
| **Won't（本期不做）** | 机器人（外挂智齿）、商机/商机券（现网已注释）、公海（现网入口被注释）、Webcall、双向回呼 | 低频或能力残缺 |

### MVP 范围（能接打电话 + 基本运营）

| 模块 | 简化到什么程度 | 人天 |
|---|---|---|
| P0 平台底座 | 登录 + 菜单 + 基础角色（不做复杂数据权限） | 60 |
| P1 媒体底座 | 单实例 + SIP 注册 + trunk + 录音 | 70 |

## 六、如果现在不重写，必须先做的治理（5~8 人天，收益最高）

这些是**当前系统随时可能出事**的点，与重不重写无关：

1. **改大 RTP 端口**：`rtpstart=10000 / rtpend=10005` → 并发只有约 **3 路**。改成 10000-20000。（0.5 人天）
2. **清 156 磁盘**：96%（剩 1.3G），`/opt1` 5.8G 大半是备份、`/var/log` 1.6G。（1 人天）
3. **降 JVM 内存**：`-Xmx2048M` 在只有 2.8G 内存的机器上跑多个实例 → 降到 512M。（0.5 人天）
4. **补开机自启**：156 **完全没有自启**，重启即全站瘫痪。（1~2 人天）
5. **恢复 ass_monitor cron + 给 asteriskGuard 加真正的重启动作**。（1 人天）
6. **消除单点**：488/489/490/491 全挤在 `gz.ydx.159.0`，`.1`~`.9` 空着 → 至少分散开。（1~2 人天）

## 七、建议的现代技术栈（对照现网）

| 层 | 现网 | 建议 | 理由 |
|---|---|---|---|
| 语音 | Asterisk 1.4.44 + chan_sip + AEL | **Asterisk 20 LTS**（后续 PJSIP）或 FreeSWITCH | 20 仍保留 chan_sip，配置可平移 |
| 录音 | `Monitor()`（res_monitor） | `MixMonitor()` | res_monitor 在新版已删除 |
| 后端 | Node6(Express3) + Java6 自研 HTTP | **Java 17 + Spring Boot 3**（话务/业务）+ **Node 20/NestJS**（推送、IM） | 长连接推送 Node 更合适，不要全转 Java |
| 协议 | `action=` 私有 RPC | 内部 REST/JSON + **老协议适配层** | 保护前端投资 |
| 数据 | MongoDB 3.2 | **PostgreSQL**（关系强的：租户/计费/工单）+ **MongoDB 7**（配置类、客户自定义字段） | 客户字段 schema-less，Mongo 更合适 |
| 缓存 | Redis 3.2 | Redis 7（哨兵/集群） | |
| 检索 | ES 2.4 + Solr | OpenSearch/ES 8（二选一即可） | 现网两套检索是历史冗余 |
| 前端 | ExtJS（102 万行） | Vue3 + TypeScript（坐席工作台） | |
| 部署 | 手工 nohup | **Docker Compose / K8S**；**媒体层用 DaemonSet + hostNetwork 固定 IP/端口** | 话机里写死了地址，IP/端口不能变 |
| 配置 | 文件 + 重启生效 | ConfigMap + 热加载 | 但 `/etc/asterisk` 必须 RWX（页面改 IVR 会写回 .ael 再 reload） |

## 十、最大的三个风险

1. **话务状态机的隐性语义**：坐席的"忙碌/小休/通话中/示闲"以及转接、监听、强插、三方、队列溢出等组合行为，
   散落在 AEL、AGI、Node、Java 四处，**没有任何一份文档说清**。重建时必须有熟悉现网业务的人全程参与。
2. **dialplan 渲染链路**：页面配置 → Mongo/`.conf` → `ass` 渲染成 `.ael` → reload，这条链路是黑盒（ass 源码 1,186 文件，OSGi，未经验证）。
3. **源码 ≠ 测试环境部署版本**：已实测 157 的 yy-server 与本地源码不一致。任何"照着源码重写"的前提是先做**版本对齐**（比对 SVN 版本/构建时间/关键类 diff）。
