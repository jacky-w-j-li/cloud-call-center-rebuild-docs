## ⚠️ 〇、环境口径声明（读全文前必看）

本套文档中出现的三台机器 **192.168.1.156 / 157 / 159 是本机 VMware 虚拟机，属于本地测试/验证环境，不是生产系统**。
文中凡"测试环境实测""部署路径""现网配置"等表述，指的都是这一套测试环境。

| 术语 | 真实含义 |
|---|---|
| **测试环境 / 本机 VMware 环境** | 192.168.1.156 / 157 / 159 三台虚机。**本文档中所有实测数据的来源** |
| **原厂 / 公有云 SaaS** | 平台原厂原厂面向多客户的公有云版本（原厂文档库口径，v1.7 / 2018）。见 16~19 篇 |
| **私有化版** | 交付给单个客户自行部署的版本。**本项目属于这一类** |

### 因此，读数据时必须注意三点

1. **规模数字不代表真实生产容量**。79 租户 / 5,767 坐席 / 6,322 分机 / 12.3 万话单，都是**测试环境里的存量**，
   部分是开户脚本批量灌的演示数据。重建容量规划时**不能用它当基线**，应按客户实际需求测算。
2. **"测试环境没跑通"≠"系统设计如此"**。典型例子：逐条话单在测试环境**没有落库**（Oracle 不可达 +
   `handler.type=mongodb` 未产出集合），但原厂设计是落 `cc_data_<YYYYMMDD>` 库的 `<Account>_c5_call_sheet`。
   凡文中出现"未落库/未启用/count=0"，都要先问一句：**是设计如此，还是这台测试机没配好？**（见 15 §11）
3. **测试环境的缺陷不等于产品缺陷**。RTP 只开 6 个端口、无开机自启、Mongo 非副本集、156 磁盘 96%……
   这些是**这台测试机的部署问题**，原厂规范（19 篇）其实要求 mongo 分片+副本、crontab 守护进程等。
   重建时应以 **19 篇原厂规范为准**，而不是照抄测试环境的现状。

> 版本口径也分三层：**原厂公有云 v1.7**（16~19 篇） vs **私有化早期版**（测试环境实际跑的） vs **本地源码快照**（`D:\lwj\`）。
> 三者存在差异，冲突时：**功能语义以原厂文档为准，实际行为以测试环境为准，实现细节以源码为准**。

## 一、这套系统是什么

**定位**：云呼叫中心 + 全渠道客服 + 云电销 + 计费运营，四合一的**多租户 SaaS**。

**血缘**：内核是**平台原厂**云呼叫中心产品的私有化交付版本，由第三方做了重打包与二次开发（私有化部署分支，代号 `gddx`）。
证据：Java 包名 `com.m7.cc.fss.*` / `com.dishui.*`、MongoDB 口令统一为 `7moorcom`、SVN 路径 `/7moor-dev/cc`、ES 集群名 `7moor-elasticsearch`、配置文件里残留 `*.7moor.com` 域名。

**交付形态**：不是一套产品，是 **30+ 个独立进程** 松耦合拼起来的系统（Node 服务 + Java 服务 + Asterisk 多实例 + 自研 AGI 服务 + MongoDB/Redis/MySQL/ES/Solr + Consul + nginx）。

### 1.1 关于文中保留的历史命名（阅读前须知）

本套文档已做**去品牌化处理**：正文叙述中不再出现任何厂商与客户名称，统一称 **平台原厂 / 私有化部署分支**。
但下列**技术标识符是环境里客观存在的字符串**，为**保证命令可执行、路径可定位、配置可对照**而保留原样：

| 保留项 | 出现形式 | 为什么不能改 |
|---|---|---|
| `gddx` | 目录 `/opt1/cc-server-in-gddx/`、进程 `yy-java-gddx`、类 `GddxCdrTask` | 本次私有化部署的**分支代号**，贯穿全部路径与进程名。改了则所有运维命令失效 |
| `7moorcom` | MongoDB / Redis **口令** | 凭据。改成占位符就连不上库、验不了数据 |
| `7moorsolr` 、`7moor-elasticsearch` | Solr 上下文路径、ES 集群名 | 是服务实际注册的名字，属于配置值 |
| `/7moor-dev/cc` | SVN 仓库路径 | 源码树里的真实路径 |
| `com.m7.cc.fss.*` | Java 包名 | 代码事实，改了源码对不上 |
| `D:\lwj\容联\` | **本机源码根目录名** | 9 万余文件的真实目录，改了找不到源码 |

> **重建时请自行命名**：上述均为历史遗留命名，新系统应使用自己的口令、路径与包名。
> 文中保留它们只为**能与现有环境逐条对照复核**，不代表建议沿用。

**阅读顺序建议**：
- **先看 16**——先知道有一套原厂文档库，再看别人反推的结论，能立刻分辨"哪些是事实、哪些是推测"
- 先搞懂"这是什么、用户怎么用" → **17 → 11 → 01 → 02**（17 是原厂口径，11 是反推口径）
- 想判断"能不能做/要多久" → 01 → 02 → 08
- **要动手写代码 → 15（逻辑）→ 12（规格）→ 17 + 图集（界面）→ 03/04/05/06（实现依据）**
- 要接电话线路 → 03（最难、最不可替代的一章） + 15 §1~§3 + 19 §19.2（PBX 部署规范）
- **要对外对接 → 18 §A**（14 个接口，含 URL/参数/鉴权/错误码）
- **要建库建表 → 18 §B**（通话/工单/会话集合字段与外键，含 `c5_call_sheet` 全字段）
- 要上线维护 → 07（现状）+ **19（原厂规范）** + 09（坑）
- 要写测试用例 / 培训客户 → **13** / **17**
- 要看界面长什么样 → **图集**（1287 张）/ 14（线框图）

> **11~19 的关系**：分**两条来源**，互相印证
> - **反推链**（读源码+测试环境实测）：11 用户操作 · 12 字段与状态机 · 13 验收 · 14 线框 · 15 代码逻辑
> - **原厂链**（系统自带文档）：16 索引 · 17 操作手册 · 18 接口与数据 · 19 部署运维 · **图集 1287 张界面**
> - **冲突时以测试环境实测为准**（原厂文档是公有云 v1.7 口径，本机测试环境是私有化早期版，详见 16 §16.3）

> **11 / 12 / 13 / 14 / 15 的关系**（这五篇是"能重建"的落地层）：
> - **15 逻辑**（谁调谁、改哪个状态、写哪张表）· 11 用户视角的操作步骤 ·
>   12 开发视角的字段与状态机 · 13 验收视角的判定标准 · 14 视觉视角的页面布局
> - 五者覆盖同一批功能点，**编号不互通但内容一一对应**
>   （11 的 3.2 ≈ 12 的 M11 ≈ 13 的 P3 组 ≈ 14 的第 4 节 ≈ 15 的 §1~§2）
> - **15 是唯一回答"代码逻辑"的一篇**：只有它能支撑"照着代码重写一遍"，
>   其余四篇讲的是"做出来的东西长什么样、怎么用、怎么验"。

## 四、文档约定

- **【实测】**：在测试环境或源码里直接验证过的结论。
- **【推断】**：从函数名/配置项语义推断，未做运行时验证。
- **【待确认】**：源码和测试环境都没找到确证。
- 路径写法：Linux 部署路径用 `/` 开头；源码路径是 Windows 本地 `D:\lwj\...`。
- 所有密码、IP 均为内网测试环境真实值，**文档含敏感信息，禁止外传**。

## 五、一句话总览（给管理层）

这是一套 2013~2017 年技术栈（Asterisk 1.4.44 / Node 6 / Java 6 / MongoDB 3.x / ExtJS）的呼叫中心 SaaS，
核心资产不是 Web 层，而是 **Asterisk AEL  dialplan 编排出来的 IVR/话务引擎** 和 **坐席话务状态机**；
Web 层（Node + Java + ExtJS 共约 170 万行）是为这套引擎做配置与运营的壳。
重建难点在**语音/话务语义的还原**，不在页面数量。
