## ⚠️ 先读这一节：三层口径（最容易搞混的地方）

文档中出现的"系统行为 / 配置 / 规模数字"来自三个不同来源，**结论冲突时有明确优先级**：

| 层级 | 是什么 | 用在哪 |
|---|---|---|
| **A. 原厂公有云 SaaS v1.7** | 系统自带的 54 份原厂文档（产品白皮书、分模块操作手册、接口规格、部署运维手册） | 对应文档集 **16 / 17 / 18 / 19** 篇 —— **重建时应以此为规范依据** |
| **B. 私有化早期版（测试环境实际在跑的）** | 本机 VMware 测试机 192.168.1.156/157/159 上实测得到的行为 | 对应 **01~15** 篇 —— 用于理解"现状长什么样" |
| **C. 本地源码快照** | `D:\lwj\` 下的反编译/源码 | 对应 **15** 篇 —— 实现细节以源码为准 |

**冲突裁决规则**：
1. 功能语义（这个按钮应该干什么）→ 以 **A（原厂文档）** 为准；
2. 实际行为（这台机器上实际干了什么）→ 以 **B（测试环境实测）** 为准；
3. 实现细节（代码里怎么调的）→ 以 **C（源码）** 为准。

**三条极易踩的推论**：
1. 文档里的规模数字（79 租户 / 5767 坐席 / 12.3 万话单）是**测试环境存量数据（含灌数）**，**不可当作容量基线**。
2. 文档里"测试环境没落库 / 没启用 / count=0"**不等于设计如此**，只说明那台机器没配好（最典型的是话单）。
3. 测试环境的缺陷（RTP 只开 6 个端口、无自启动、Mongo 非副本集）属于**部署问题**；重建请按 **19 篇（原厂部署运维规范）** 做，**不要照抄 07 篇现状**。

**判断口诀**：代码里写死的 = 设计固有（照做）；配置文件里没填/没设的 = 部署没配好（要修）。

另外注意两套菜单口径差异：原厂 v1.7 是 14 个菜单、称「工单模块」、路径 `设置→渠道设置`；测试环境跑的是私有化早期版，10 个菜单、称「业务模块」、路径 `设置→高级功能→通话配置`。

## 重建工作量速览（详见 `docs/08_重建路线图.md`）

- **19 个模块（P0~P18）**，含前后端，合计约 **1,320 ~ 1,920 人天**
- **MVP 裁剪后 ≈ 495 人天**（6~7 人 / 5~6 个月）
- **关键路径严格串行、不可压缩**：
  `P1 媒体底座（Asterisk/SIP/RTP）` → `P2 话务核心（呼入/外呼/CTI）` → `P3 IVR 引擎`

### 技术选型硬约束（改一样就全盘皆变）
- 全系统命门是**私有 RPC**：`action=xxx&data={}`（C5Action / C5Response + XML），贯穿 前端 ↔ Node(3000) ↔ Java(9999)。**不是 REST**，改造必须先做协议适配层。
- 坐席端前端是 **jQuery1.x + Bootstrap2 + 自研 DS 框架 + LABjs**（`compress.json` 合包，无 webpack），**不是 ExtJS**；ExtJS 4.0.7 只用在计费/运营后台。
- 出局选路是**配额加权轮询**（非主备），无健康检查。
- CTI 状态**不落库**（进程内存 + AMI 队列成员态）→ 服务重启 = 全坐席状态丢失。
- 计费金额单位 = **元 × 10000**，扣款不校验余额。

| 块 | 体积 | 处置 | 原因 |
|---|---|---|---|
| `运行环境程序备份/`（156/157/159 三台机器整目录 dump） | 1.9 GB | ❌ 剔除 | 部署产物，含真实配置、业务数据、口令，不是源码 |
| `自建平台代码及文档/安装软件包/` | 805 MB | ❌ 剔除 | 第三方安装包（JDK/Node/Mongo 等），可从官网获取 |

**code/ 内部剔除了什么**（1,466 MB → 114 MB）：

- `*.jar` 308 MB —— 编译产物 + 依赖（poi、spring、mina 等，多份重复）
