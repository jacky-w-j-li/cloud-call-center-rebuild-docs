# 计费后台「跳转云客服 / 云电销」报错 — 排查与修复报告

> ⚠️ **环境口径**：本报告涉及的 192.168.1.156 / 157 / 158 / 159 均为**本机 VMware 虚拟机（测试/验证环境）**，**不是生产系统**。
> 文中实测数据、规模数字、配置现状都来自该测试环境，不代表真实生产规模与规范。


- 日期：2026-09-12
- 现象：在 `http://192.168.1.157:8000`（计费后台）账号管理页，选一个账号点「跳转云客服 / 云电销 / 云客服管理后台」，全部弹 `unknow error!`
- 结论：**已修复**，三个跳转均返回 `success:true` 并成功打开目标页面

## 一、真正的根因

**不是前端坏了，也不是云客服坏了，是 yy-server 本地配置文件里写死了错误的地址。**

跳转由 157 上的 yy-server（`/opt/yy-server-gddx`，监听 3000）处理，nginx 把 `157:8000/action` 反代到 `127.0.0.1:3000`。
关键文件：`/opt/yy-server-gddx/serverConfig.json`

| 配置项 | 修复前（错误） | 修复后 | 说明 |
|---|---|---|---|
| `ccServerUrl` | `http://192.168.1.155/` | `http://192.168.1.156:80/` | 155 这台机器**根本不存在** |
| `ccInUrl` | `http://192.168.1.155/` | `http://192.168.1.156:80/` | 同上 |
| `ccInRedirect` | `http://14.29.4.196/` | `http://192.168.1.156:80/` | 公网地址，内网不可达 |
| `ccOutUrl` | `http://172.42.38.22/` | `http://192.168.1.156:8002/` | 另一网段，不可达 |
| `ccOutRedirect` | `http://14.29.4.227/` | `http://192.168.1.156:8002/` | 公网地址，内网不可达 |

### 三个 action 与字段的对应关系（157 上的实际代码）

文件 `7moor/ucenter/BillLoginHandler.js`：

| action | 取 session 的 API 地址 | 浏览器跳转地址 |
|---|---|---|
| `redirectCCAdminLogin` (L292) | `ccServerUrl` + `service?action=getLoginSession` | `ccServerUrl` + `?sessionId=` |
| `redirectCCInLogin` (L323) | `ccInUrl` + `service?...` | `ccInRedirect` + `?sessionId=` |
| `redirectCCOutLogin` (L355) | `ccOutUrl` + `service?...` | `ccOutRedirect` + `?sessionId=` |

> 注意：157 上的代码与本地源码树 `自建/yy-server` 的版本**不一致**（本地版 `redirectCCInLogin` 用 `ccServerUrl`，157 版用 `ccInUrl`）。排查必须以服务器实际代码为准。

## 二、关于 Consul（此前的判断需要修正）

先前判断「Consul 里没有 `cc-server-in` 注册」是**次要问题，不是直接根因**：

- Consul KV 里 `_gw/_vt_v-release/_sn_yy-server/{ccInUrl,ccInUrlNew,ccOutUrl}` 原本是公网域名 `ykf/kf/ydx.tycc100.com`。
- 但实测 **KV 没有覆盖本地 `serverConfig.json`**：日志里的地址是 `192.168.1.155`，既不是 KV 里的公网域名，也不是被 KV 覆盖后的值 —— 说明生效的是本地文件。
- 也就是说，即便 KV 改对了，跳转仍然会失败。

**「cc-server-in 启动了会自动注册吗？」——不会。** 依据：

1. `/root/start_cc.sh` 里**只有启动 consul agent**，没有任何服务注册步骤。
2. `cc-server-in-gddx` 的 `node_modules` 里**连 consul 客户端库都没有**，不具备自注册能力。
3. Consul 里现有那 9 个服务（billDB、ccRedis、cccdr、clogDB、commonDB、esTcp、reportDB、yy-server 等）都是**历史上通过 API 注册后持久化在 `/opt1/consul/data/services`**，agent 重启时从 data-dir 恢复 —— 看起来像"自动注册"，其实是陈旧的历史注册。
4. `/etc/consul.d/services.json` 内容是 `{"services": []}`，即空配置。

（本次仍顺手把 `cc-server-in` 注册进了 Consul → `192.168.1.156:3000`，health check 已 passing，便于其他走服务发现的调用方。）

## 三、已执行的修复

```bash
# 1) 备份并修正 yy-server 配置（157）
cd /opt/yy-server-gddx
cp serverConfig.json serverConfig.json.bak.20260912
# 将 ccServerUrl / ccInUrl / ccInRedirect → http://192.168.1.156:80/
# 将 ccOutUrl / ccOutRedirect          → http://192.168.1.156:8002/

# 2) 重启 yy-server（配置是进程启动时加载的，必须重启）
#    kill 掉 3000 端口的进程后：
cd /opt/yy-server-gddx && setsid nohup /opt/node/bin/node app.js > /tmp/yy_restart.log 2>&1 < /dev/null &

# 3) 启动 cc-server-out（云电销后端 13001，此前未运行，导致 156:8002/service 返回 502）
cd /opt1/cc-server-out-gddx && setsid nohup /opt/node/bin/node startup.js > /tmp/ccout.log 2>&1 < /dev/null &

# 4) 顺带在 Consul 注册 cc-server-in → 192.168.1.156:3000（health: passing）
```

### 为什么 `156:80` 一个地址能同时当 API 和页面地址

156 的 nginx 把 `/service` 反代到 `192.168.1.156:3000`（cc-server-in），`/` 返回云客服前端页面。
所以 `http://192.168.1.156:80/` 既满足服务端 `getLoginSession` 调用，又能作为浏览器落地页。
`156:8002` 同理：nginx → `13001`（cc-server-out）+ 云电销前端页面。

## 五、补充修复：跳转到「用户中心」（2026-09-13）

现象：选账号（如 `gddx`）后点「跳转到用户中心」报错。

**这条链路和前面三个完全不同**：不是 `window.open` + `/action`，而是隐藏 form **POST 到 `./public`**，action 为 `bill.getSessionId`
（`7moor/ucenter/BillLoginHandler.js:49`，路由 `routes/publicHandler.js:89`）。成功后返回一段 HTML：
`window.location = config.ucenterUrl + '/?sid=' + rep.sessionId`；失败则返回「自动登录失败，请重试」。

| 项 | 内容 |
|---|---|
| 根因 | `serverConfig.json` 的 `ucenterUrl` = `http://14.29.4.228/`（公网），内网不可达（socket hang up） |
| 用户中心实际位置 | **157:80**（nginx `root /opt/ucenter-gddx`，`server_name user.7moor.com`，页面 title=用户中心） |
| 修复 | `ucenterUrl` → `http://192.168.1.157`（**去掉尾斜杠**，否则代码拼出 `//?sid=`） |
| 备份 | `/opt/yy-server-gddx/serverConfig.json.bak.20260913` |

验证：

```
POST 157:8000/public  action=bill.getSessionId
→ url='http://192.168.1.157/?sid=e4435620-...'     （修复前为 http://14.29.4.228//?sid=...）
GET  http://192.168.1.157/  → HTTP 200，title=用户中心
sid 已写入 bill.bill_system_session，account = gddx / N00000000419 / 客户方  ← 有效会话，非白屏
```

补充：ucenter 前端**没有**硬编码公网地址（唯一一处 `http://14.29.4.196/im_win_gdd` 与本跳转无关），所以改服务端配置即可。

## 六、遗留问题 / 风险

0. **四个跳转的配置字段速查**（都在 `/opt/yy-server-gddx/serverConfig.json`，改完必须重启 yy-server）：

   | 跳转 | API 地址字段 | 浏览器落地字段 |
   |---|---|---|
   | 云客服管理后台 | `ccServerUrl` | `ccServerUrl` |
   | 云客服 | `ccInUrl` | `ccInRedirect` |
   | 云电销 | `ccOutUrl` | `ccOutRedirect` |
   | 用户中心 | — | `ucenterUrl`（走 `/public` + `bill.getSessionId`） |

1. **服务均为手动 `setsid nohup` 启动，无开机自启**。重启主机会再次失效：
   - 157:3000 yy-server
   - 156:13001 cc-server-out
2. **156:13000 仍是 down**（Consul 里 `yy-server` 注册指向它，state=critical），这是陈旧/错误的注册，实际 yy-server 在 157:3000。暂未改动，避免影响其他走服务发现的调用方。
3. `cc-server-in` 的 `serverConfig.json` 里 `yyBillUrl` 指向 `156:13000`，依赖上述未启动的服务，相关账单功能可能异常。
4. 备份文件：`/opt/yy-server-gddx/serverConfig.json.bak.20260912`

## 七、排查中踩到的坑（供复用）

- **`pgrep -f "node app.js"` 会匹配到执行它的 shell 自身**（命令行里含该字符串），导致 `kill` 自杀、SSH 会话中断。改用 `netstat -tlnp | grep :3000` 取精确 PID。
- ssh2 执行 `setsid nohup ... &` 后 exec 的 stream 常不触发 close，脚本会挂住 —— 需加全局超时兜底，且启动命令放最后一步。
- 本地源码树与生产代码存在版本差异，定位时必须读服务器上的实际文件。
