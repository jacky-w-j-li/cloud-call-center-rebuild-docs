## 一、拨打 02022221112 没有声音

### 结论：呼叫根本没走到语音节点，走的是「出局 → 等待音乐」

我在 159 上用 `originate Local/02022221112@N00000000489` 实测了 dialplan 的真实走向（不打扰话机）：

```
Executing [02022221112@N00000000489:1] Set(FROM_CID=)
Executing [02022221112@N00000000489:2] Set(FROM_DID=02022221112)
Executing [02022221112@N00000000489:4] Set(dialNum=02022221112)
Executing [02022221112@N00000000489:5] AGI(agi://127.0.0.1:7891/AgiFormatDialoutNumber?...&dialnum=02022221112)
Executing [02022221112@N00000000489:6] Answer()
Executing [02022221112@N00000000489:7] Goto("N00000000489-route|902022221112|1")   ← 被加了前缀 9
Executing [902022221112@N00000000489-route:1] Goto("N00000000489-dial|902022221112|1")
Executing [902022221112@N00000000489-dial:3] Monitor(...902022221112...)
Executing [902022221112@N00000000489-call:1] MusicOnHold()                          ← 放的是等待音乐
Started music on hold, class 'default', on Local/...
Spawn extension (N00000000489-call, 902022221112, 1) exited non-zero
```

### 三层原因（按影响顺序）

**1. 号码被当成出局号码，不是呼入服务号**

分机 context `N00000000489` 只有两条规则：`0000` 和 `_X.`。拨任何号码都进 `_X.`，其中的
`AgiFormatDialoutNumber` 会给号码**加出局前缀 9**：

```
02022221112  →  902022221112
10008        →  910008        （我另外测的内部语音节点号，同样被加 9）
```

加 9 之后在 `N00000000489-route` 里匹配不到精确条目，落到 `_9X.` → `MusicOnHold()`。

**决定性佐证**：你的通话记录里录音名是
`20260914-235454_N00000000489_20008671_**902022221112**_cc-ali-0-1789401294.2.mp3`
——和我实测产生的 `902022221112` 完全一致，说明你那通电话就是走的这条路径。

> `02022221112` 是**服务号（呼入号码）**，它的 IVR 流程在 `serviceno.ael` 的
> `context 02022221112`，默认日程 → `ToPeerType=ivr_node_text_announcement, ToPeer=10008`。
> 这套流程**只有呼入才会触发**；从软电话拨出去是出局方向，永远进不去。

**2. 分机编码不匹配（即使放音你也听不到）**

```
[20008671]  ExtenType=gateway   disallow=all   allow=g729      ← 只有 G.729
MicroSIP    audioCodecs=PCMA/8000/1 PCMU/8000/1                ← 只有 G.711
```

日志实锤：`NOTICE chan_sip.c: No compatible codecs, not accepting this offer!`
（和你上一通 02022222222 完全一样）

**3. 即便进了 IVR，语音节点还依赖阿里 TTS**

默认日程指向 `10008`，是**文本语音节点**（`agittszh` → 阿里 TTS，`/opt/aliTtsServer`，159 上 PID 6433）。
159 有外网（baidu 200、阿里云域名可解析），但 `aliTtsServer` 日志里**最近一条合成请求都没有**——
进一步印证呼叫从没走到过放音环节。

### 建议

| 目的 | 做法 |
|---|---|
| 至少让软电话能通 | 换 **sip 类型分机 `20008660` / `gmwnrzrr`**（Codecs `gsm\|alaw\|g729`，alaw 优先），SIP 服务器 `192.168.1.159:6060`，编码勾 PCMA。已实测 `401 → 200 OK` |
| 听服务号的 IVR 语音 | 服务号是**呼入**触发的，软电话外呼打不通。要验证得模拟呼入：从 trunk/SIP 中继打进 `02022221112`，或让 Asterisk `originate` 直接进 `context 02022221112` |
| 内部拨号听节点语音 | 实测拨 `10008` 也会被加 9 → MusicOnHold，**同样到不了**。需先修正 `AgiFormatDialoutNumber` 的出局前缀逻辑，或改用呼入方式验证 |

> 规律再确认一次：`ExtenType=gateway` 的分机几乎都是 G.729 独占（出局中继用）；
> **软电话必须注册 `ExtenType=sip` 的分机**。

## 四、排查中踩到的坑

1. **别用 `asterisk -rx`**，多实例环境下连不上；必须带 `-C <实例的 asterisk.conf>`。
2. **`channel originate` 在这个版本不存在**，正确写法是 `originate <tech/res> extension <exten>@<ctx>`。
3. **测 dialplan 用 `Local/` 通道最干净**：`originate Local/10008@N00000000489 application Wait(3)`
   不会打扰真实话机，还能完整看到 dialplan 走向。
4. ** Asterisk 默认日志级别看不到拨号细节**，需要先 `core set verbose 10` 再测。
5. 前端文案要连着 `handler/` 和 `config/` 两个目录一起 grep，错误码是 `action短名_错误码` 拼出来的 key。
