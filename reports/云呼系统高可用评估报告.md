# 云呼系统高可用性评估报告

> ⚠️ **环境口径**：本报告涉及的 192.168.1.156 / 157 / 158 / 159 均为**本机 VMware 虚拟机（测试/验证环境）**，**不是生产系统**。
> 文中实测数据、规模数字、配置现状都来自该测试环境，不代表真实生产规模与规范。


评估时间：2026-10-19 00:07 ~ 00:20
评估方式：SSH 实地盘查 156 / 157 / 159 三台主机（进程、配置、日志、crontab、rc.local、数据层复制状态）
核心问题：**通话过程中服务崩溃，会不会影响通话和信令？**

---

## 一、直接结论

**先回答你最关心的问题：业务服务崩溃，确实不影响已建立的通话。** 但整个系统有三个"一崩就断"的单点，都在媒体/信令路径上。

| 失效对象 | 已建立的通话 | 新呼叫建立 | 说明 |
|---|---|---|---|
| cc-server-in / cc-java-in / cc-socket-push | ✅ 不受影响 | ⚠️ 坐席无法操作 | 云客服 Web 端失效，电话照打 |
| yy-server / bill / report / ES / Solr | ✅ 不受影响 | ✅ 不受影响 | 纯业务侧 |
| MongoDB / MySQL / Redis | ✅ 不受影响 | ⚠️ 部分 | CDR 丢失、坐席状态异常 |
| **ASS（7891 / 8090）** | ✅ 不受影响 | ❌ **全部失败** | 85 处 AGI 依赖 |
| **Asterisk 实例（gz.ydx.159.0）** | ❌ **立即中断** | ❌ **全部失败** | **全租户单点** |
| **Asterisk gateway 实例（5072）** | ❌ 出局中断 | ❌ 出局失败 | 出局唯一通道 |
| 物理机宕机 | ❌ 全断 | ❌ 全断 | 无跨机冗余 |

**判断依据（Asterisk 的架构特性）**：SIP 信令状态机、RTP 媒体流、channel 桥接全部在 Asterisk 进程内自包含。dialplan 里的 AGI 是**呼叫建立阶段的同步阻塞调用**，一旦进入 `Bridge()` / RTP 直通，就不再依赖任何外部服务。所以媒体面的故障域 = Asterisk 进程本身。

## 二、组件冗余矩阵（实测）

### 2.1 媒体 / 信令层

| 主机 | 实例 | 端口 | 承载 | 冗余 |
|---|---|---|---|---|
| 159 | `gz.ydx.159.0` | UDP 6060 | **租户 488/489/490/491 全部** | ❌ **单点** |
| 159 | `gz.ydx.159.1`~`.9` | UDP 6061-6069 | **空跑，无租户** | 名义冗余，实际不可用 |
| 159 | `gateway` | UDP 5072 | 出局中继 | ❌ 单点 |
| 156 | `gd.zj.1.0` | UDP 6060 | 156 上租户坐席 | ❌ 单点 |
| 156 | `gateway` | — | — | ❌ 单点 |
| 159 / 157 | `clpms`（FreeSWITCH 改名） | TCP 5066/5074 | 出局接力 | ❌ 单点 |

**这里有个反直觉的坑**：`gz.ydx.159.1` ~ `.9` 看起来是 9 个备份实例，实测是**空跑**：

```
$ ls /etc/asterisk/gz.ydx.159.0/accounts/  → N00000000488 N00000000489 N00000000490 N00000000491
$ ls /etc/asterisk/gz.ydx.159.1/accounts/  → （空）
$ ls /etc/asterisk/gz.ydx.159.9/accounts/  → （空）

$ asterisk -C .../gz.ydx.159.1/asterisk.conf -rx "sip show peers"
gateway   192.168.1.159   N  5072  OK (1 ms)
8009      (Unspecified)   D  N  0   Unmonitored     ← 8000~8009 从未注册
```

每个实例 63 个 peer 全是 `8000~8009` 这类默认测试分机 + gateway，**没有 6 位真实分机**（`grep -cE "^\[[0-9]{6,}\]"` = 0）。所以这 9 个实例是"预留容量"，**`.0` 挂了它们接不了任何东西**。

### 2.2 呼叫控制层（AGI / 状态）

```
$ grep -rhoE "agi://[0-9.]+:[0-9]+" /etc/asterisk/gz.ydx.159.0/ | sort | uniq -c
     85 agi://127.0.0.1:7891
```

**85 处 AGI 全部指向本机 7891（ASS）**，无备选地址。调用点包括：

| AGI | 作用 | 调用时机 |
|---|---|---|
| `AgiDialin` | 呼入路由 | 建立 |
| `AgiFormatDialoutNumber` | 出局号码格式化（加前缀 9） | 建立 |
| `gaicalllimit` | 并发呼叫限制 | 建立 |
| `AgiCallinNumAndBlackNum` | 黑名单判断 | 建立 |
| `AgiIsLocalNumber` | 内线判断 | 建立 |
| `agisiplogin` / `AgiProcessIvrLogin` | 坐席签入 | IVR 交互中 |
| `agiChatingIvrSetVar` | IVR 变量 | IVR 交互中 |

→ **ASS 挂掉：所有新呼叫建立失败；IVR 进行中的通话卡住；但已 Bridge 的坐席↔客户通话存活。**

### 2.3 业务层（156 为主）

| 服务 | 端口 | 实例数 | 崩溃影响 |
|---|---|---|---|
| cc-server-in | 3000 | 1 | 云客服 Web 不可用，**通话不受影响** |
| cc-java-in | 9999 | 1 | 同上 |
| cc-socket-push | 5004 | 1 | 消息推送失效 |
| cc-server-out | 13001 | 1 | 外呼端不可用 |
| ASS | 8090 | 1 | 156 侧呼叫建立失败 |
| cccdr | — | 1 | CDR 丢失，通话不受影响 |

### 2.4 数据层 —— 全部单点，零复制

| 组件 | 实测结果 | 结论 |
|---|---|---|
| MongoDB 156 | `rs.status()` → `s.members is undefined` | ❌ 非副本集，单机 |
| MongoDB 157 | `bindIp: 127.0.0.1`，仅本机可连 | ❌ 单机 |
| Redis 156 | `role:master` / `connected_slaves:0` | ❌ 无从库 |
| Redis 157 | `role:master` / `connected_slaves:0` | ❌ 无从库 |
| MySQL 156 | 单实例 | ❌ 无复制 |
| ES 157 | 单节点 | ❌ 无集群 |

### 2.5 治理层 —— 唯一有冗余的部分

```
$ curl -s localhost:8500/v1/status/peers
["192.168.1.156:8300","192.168.1.157:8300","192.168.1.159:8300","192.168.1.161:8300"]
$ curl -s localhost:8500/v1/status/leader
"192.168.1.157:8300"
```

Consul 3 节点（156/157/159），Raft 可容忍 1 节点失败。**但 161 是僵尸 peer**（`ping` DOWN，不在 catalog 里）——只出现在 serf 持久状态中。

**重要**：业务服务**不会自注册**到 Consul（`/etc/consul.d/services.json` = `{"services":[]}`），现存 9 个服务是从 `/opt1/consul/data/services` 恢复的陈旧注册。所以 Consul 的冗余**对通话没有任何保护意义**——它甚至不知道 Asterisk 在哪里。

## 三、自愈能力实测（这块比预想的差）

### 3.1 三台主机的开机自启动

| 主机 | 自启动方式 | 覆盖度 |
|---|---|---|
| **159** | `/etc/rc.d/rc.local` 完整脚本 | ✅ 10 个 Asterisk + gateway + ass + nginx + asteriskGuard + clpms + ASR/TTS |
| **157** | rc.local 只有 nginx + clpms；mongod 走 chkconfig | ⚠️ 部分 |
| **156** | **无**（rc.local 是空模板，systemd 只有系统基础服务） | ❌ 需手动 `start_cc.sh` |

156 的 systemd enabled 列表里，业务相关的一个都没有（只有 atd/crond/rsyslog/tuned 等），rc.local 是 CentOS 7 默认模板，`crontab -l` 只有 `0hourly` / `raid-check` / `sysstat`。

→ **156 重启后，整套业务全部要人工 `sh /root/start_cc.sh`。**

### 3.2 asteriskGuard —— 只监控，不重启

159 上有 `/opt/asteriskGuard/asteriskGuard.jar`（PID 6233 在跑），配置：

```properties
asterisk.ip=gz.ydx.159.0:6060,gz.ydx.159.1:6061,...,gz.ydx.159.9:6069,gateway:5072
mail.to=<运维告警收件邮箱>
check.ass.log.agi.tcp=yes
ass.log.dir=/var/log/ass/
restart.ass.warning.name=gz.ydx.159.x
```

看着像看门狗，但实测日志：

```
$ grep -iE "restart|down|unreach|dead|stopped|kill" /var/log/asteriskGuard/monitor_0_0.log
（零命中）

$ tail -6 /var/log/asteriskGuard/monitor_0_0.log
[INFO] 2026-10-19 00:14:00 - com.m7.monitor.Monitor.monitorSip
monitor:gz.ydx.159.0--6060
[INFO] 2026-10-19 00:14:15 - com.m7.monitor.Monitor.monitorSip
monitor:gz.ydx.159.1--6061
```

只有 15 秒一轮的轮询记录（11 个实例轮一圈约 165 秒），**从未执行过重启**。`assLogMonitor` 也只是循环打印 `check....`。

所有 Asterisk 进程 **PPID = 1**（无守护父进程），崩溃后直接消失。

### 3.3 ASS 的看门狗已被停用

```bash
$ crontab -l
0 0 * * * /srv/scripts/nginx_cutlog.sh
0 1 * * * /srv/scripts/clear_asterisklog.sh
0 4 * * * /srv/scripts/gateway_restart.sh
#* * * * * /srv/scripts/ass_monitor.sh          ← 注释掉了
#* * * * * sleep 15;/srv/scripts/ass_monitor.sh
```

`ass_monitor.sh` 逻辑是"ASS 进程数=0 就 `/opt/ass/ass.sh start`"，是有效的自愈。但**四行全部被注释**。`/var/log/ass_monitor.log` 最后记录停在 **2023-06-13**：

```
ASS running on 2023-06-13-16-20-46
ASS is down  2023-06-13-16-20-16     ← 最后一次触发重启
```

→ **ASS 自愈能力从 2023-06 起就失效了。**

### 3.4 存在的计划内中断

```bash
$ cat /srv/scripts/gateway_restart.sh
/usr/sbin/asterisk -r -C /etc/asterisk/gateway/asterisk.conf -vvvx 'restart now'
```

**每天 04:00 硬重启 gateway 实例** —— 所有正在进行的出局通话会在这一刻断掉。这是"设计出来的中断"，不是故障。

## 五、加固方案（按投入产出排序）

### 第一档：零成本 / 立刻可做

| # | 动作 | 命令 / 位置 |
|---|---|---|
| 1 | **156 加开机自启动** | 把 `/root/start_cc.sh` 写进 `/etc/rc.d/rc.local` 并 `chmod +x` |
| 2 | **恢复 ASS 看门狗** | 159 上取消 `ass_monitor.sh` 那 4 行 crontab 注释 |
| 3 | **156 清磁盘** | `> /var/log/ass/*.log`；清理 `/opt1/156-opt1.tar.gz`(726M)、`/opt1/OOo_3.3...tar.gz`(177M) |
| 4 | **降 Java 堆** | 156 上 `cc-java-out` / `assign-java` 的 `-Xmx2048M` 调到 512M（2.8G 内存撑不住两个 2G 堆） |
| 5 | **trunk 开健康检测** | gateway 的 `sip_trunk.conf` 加 `qualify=yes`（当前 3 个 trunk 全是 `Unmonitored`） |

### 第二档：进程级高可用（改动可控）

| # | 动作 | 说明 |
|---|---|---|
| 6 | **Asterisk systemd 化** | 每个实例一个 unit，`Restart=always` + `RestartSec=5`，替代只告警不重启的 asteriskGuard |
| 7 | **ASS systemd 化** | 同样 `Restart=always`，比分钟级 crontab 快得多 |
| 8 | **真实分片** | 把 488/489/490/491 分散到 `.0`~`.3`，缩小单实例爆炸半径（当前 100% 集中在一个进程） |
| 9 | **gateway 重启改窗口** | `gateway_restart.sh` 挪到业务低峰并加"有活跃通话则跳过"判断 |

### 第三档：架构级（真正的 HA）

你的诉求"服务崩溃不影响通话"，在**单 Asterisk 实例**下无法完全满足——进程自身崩溃就是全断。要做到这一点，需要引入 SIP 前端分发：

```
                    ┌──────────────────┐
   坐席/中继  ──────▶  Kamailio/OpenSIPS │  (SIP 负载均衡 + 注册位置共享)
                    └────────┬─────────┘
                   ┌─────────┼─────────┐
              ┌────▼───┐ ┌───▼────┐ ┌──▼─────┐
              │ Asterisk│ │Asterisk│ │Asterisk│   ← 任意一台挂掉，
              │  .0     │ │  .1    │ │  .2    │     其余接管后续注册
              └─────────┘ └────────┘ └────────┘
                   └─────────┼─────────┘
                    ┌────────▼─────────┐
                    │ Redis / DB (共享) │  ← SIP 注册位置、坐席状态
                    └──────────────────┘
```

要点：

- **Kamailio 做 dispatcher + registrar**，Asterisk 只做媒体/IVR（这是你的强项领域）
- **SIP 注册位置必须外置**（Redis / DB），否则切换后找不到 Contact
- 当前用的是 **chan_sip**（老模块），它不支持共享注册；要上这套得迁 **PJSIP + Realtime**
- 159 的 hostname 是 `dmq.test.com`，原始设计似乎考虑过 Asterisk 的 **DMQ**（分布式消息队列，用于多节点间同步 device state / MWI）。但 DMQ 依赖 PJSIP，当前这套 chan_sip 用不上
- clpms（FreeSWITCH）也建议做双节点 + 共享 DB

**坦白的权衡**：第三档是伤筋动骨的改造（chan_sip → PJSIP 迁移风险高，dialplan 要重写，现有 85 处 AGI 需要逐项验证）。如果目标是"降低故障概率"而不是"消除单点"，**先把第一档和第二档做完，收益已经很大**——真正的 HA 是运维出来的，不是架构图画出来的。

## 六、建议的验证方法（不擅自执行）

如果你要实测"业务服务崩溃对通话的影响"，可以用这条安全的路径：

```bash
# 1) 在 159 上起一个 60 秒的本地通道（不打扰任何真实话机）
cat > /var/spool/asterisk/gz.ydx.159.0/tmp/hatest.call <<EOF
Channel: Local/10008@N00000000489
Application: Wait
Data: 60
EOF

# 2) 期间在 156 上 kill 一个无状态业务服务
kill -9 $(pgrep -f "cc-socket-push")

# 3) 观察通道是否存活
asterisk -C /etc/asterisk/gz.ydx.159.0/asterisk.conf -rx "core show channels"

# 4) 恢复
cd /opt1/cc-socket-push-gddx && ./startup.sh start
```

注意 159 的 spool 目录是 `/var/spool/asterisk/gz.ydx.159.0`（非标准路径），且该版本 Asterisk **无 `originate` 应用**，只能用 call file 或 AMI（端口 **6030**，非 5038）。

## 八、一句话总结

**你的诉求在业务层已经天然满足**（业务服务崩溃不影响通话），**但在媒体层完全不满足**——所有租户挤在 `gz.ydx.159.0` 一个 Asterisk 进程里，没有自动重启、没有 failover、没有跨机冗余。最紧迫的不是架构改造，而是 **156 的磁盘（96%）、内存（剩 69M）和开机自启动** 这三件事，它们比任何架构缺陷都更可能让你明天就出故障。
